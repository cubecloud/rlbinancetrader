# Дизайн наблюдения агента — решения (обсуждение с пользователем 2026-07-25)

Живой документ. Фиксирует состав и способ подготовки наблюдения ДО реализации.
Реализовывать по этому документу; менять только с согласия пользователя.

## Источник данных и время
- Источник ВСЕГДА минутный таймфрейм (1m).
- Обучение — минутные бары из базы (PostgreSQL через dbbinance).
- Бой (paper/live) — минутные бары из freqtrade.
- Минутные данные ОБЯЗАТЕЛЬНО присутствуют в наблюдении.
- Строитель признаков ОБЩИЙ для обучения и боя (один код), источник за одним
  фасадом слоя данных. Требование парности: на одном окне признаки из базы и
  из freqtrade обязаны совпадать ПОБИТОВО (гейт, по образцу «снимок = живая
  база»).

## Каузальность (с оговоркой)
- Реально случившееся будущее (фактическая цена позже `now`) — в наблюдение
  НЕЛЬЗЯ.
- Прогнозы голов (predict_time = now, target_time в будущем) — МОЖНО: они
  выданы на текущий момент, посчитаны по прошлому, в бою тоже доступны.

## Resample к старшим таймфреймам
- Каузальный resample с якорем на ТЕКУЩУЮ минуту (скользящее окно на один
  таймфрейм назад), метод `dbbinance ... pg_resample_to_timeframe`
  (to_timeframe, last_full_bar=True, origin, use_extended_cols). Свой не пишем.
- 1h-resample (совпадает с горизонтом сигналов v7) — ДОПОЛНИТЕЛЬНО, включается
  на усмотрение реализации (RLP-агента), если сочтёт нужным. Базовый уровень —
  минутные данные.

## Блок 1 — рынок

### Цены (BTC) — ЗАФИКСИРОВАНО 2026-07-25
Способ — как `binanceenv/observations.py::prepare_ret_obs` (перевод цен в
ДОХОДНОСТИ, а не min-max):
- лог(open/high/low/close/vwap), затем относительные изменения бар-к-бару:
  x1=Δclose, x2=Δhigh, x3=Δlow, vwap_ret=Δvwap;
- внутрибарные пропорции: x4=(high−close)/close, x5=(close−low)/close;
- итог по ценам: [x1, x2, x3, x4, x5, vwap_ret].
Абсолютной цены в наблюдении НЕТ (план это и запрещал). Само по себе
нормировано, каузально, скейлер хранить не нужно.
ПРАВКА при переносе: убрать утечку `fillna(method='bfill')` (заполнение из
будущего на первом баре) — заменить на заполнение нулём/вперёд.

### Торговые числа (поток сделок из свечей) — ЗАФИКСИРОВАНО 2026-07-25
Основано на рекомендации RLP-агента (принято пользователем). Численно
проверено: `new_logarithmic_scaler` на денежных объёмах насыщается
(0.995..0.9999) — для объёмов НЕ применять. Из 4 сырых колонок 3 почти
дублируют друг друга (связаны через цену) — храним 3 безразмерных признака
вместо 4 сырых:
1. **доля агрессивных покупок** = `taker_buy_base / base_volume` (0..1;
   при base_volume=0 → нейтраль 0.5, НЕ clip);
2. **средний размер сделки** = `base_volume / trades` (различает толпу мелких
   vs крупных игроков; лог + деление на скользящую медиану; при trades=0 —
   нейтраль);
3. **относительный объём** = `log(quote_volume / rolling_median_24h)`, окно
   строго ПРОШЛОЕ (shift(1)); clip к ±3 (фикс. константа, НЕ p1..p99).
`taker_buy_quote` — ВЫКИНУТЬ (дубликат `taker_buy_base * price`).
Все три безразмерны и не зависят от года (снимают многолетний рост объёмов).

### Сигналы v7 и их составляющие (для копирования)
entry_signal / trans_entry_signal (булевы) + непрерывные составляющие
(насколько цена ниже порога покупки, bounce, leg_age и т.п.), флаг штатного
выхода (`_exit[i]`), режим рынка. Диктуется v7 (гейт немарковости Э1.2).

## Блок 2 — состояние агента (среда считает из СВОЕЙ книги, П4) — ЗАФИКСИРОВАНО 2026-07-25
Почти всё уже само-нормировано, скейлер не нужен:
- в позиции / entered_on_up / cb_active / «CB снят сегодня» — булевы 0/1, как есть;
- pos_tag one-hot — как есть (порядок категорий зафиксировать в spec);
- остаток cooldown (0..1) — как есть (делить на ТУ ЖЕ длину cooldown в train и serve);
- нереализованный PnL = `price/entry_price − 1` (доля, при желании clip ±0.5);
- откат от пика позиции = `price/peak_price − 1` (≤0);
- просадка эквити от пика = `equity/peak_equity − 1` (≤0);
  peak считать из книги среды, БЕЗ мутации внутри _obs (гейт чистоты).
Привести надо ОДНО, оно единственное неограничено сверху:
- **дней в позиции** = `tanh(days / median_hold)`, median_hold ≈ 2442 бара
  (медиана длительности сделки, из spec). НЕ делить на max по train.
- свежесть данных (возраст последнего бара) — 4-е жёсткое правило, ограничено.
Никаких min-max по эпизоду ни для одной величины (утечка масштаба).

## Философия нормировки — ЗАФИКСИРОВАНО 2026-07-25
Замороженный-на-train скейлер (min-max / z) НЕ используем для наших величин —
он вреден: μ/σ объёмов с 2021-24 на данных freqtrade 2026 систематически
уедут («байт-в-байт по коду, но враньё по смыслу»). Используем само-нормированные
формы (доходности, доли, относительный объём к скользящей медиане) — у них нет
замороженного числа, которое могло бы разойтись; их «параметр» — только длина
окна и константы (median_hold, длина cooldown, порядок one-hot), задаются в spec.
- Артефакт с хэшем (манифест) хранит СПЕЦИФИКАЦИЮ (длины окон, константы, список
  и порядок колонок, порядок one-hot), а НЕ μ/σ. Хэш — по этому spec.
- Clip: фиксированные пороги из spec (относительный объём ±3, PnL ±0.5), НЕ
  p1..p99. Assert PLAN 1.3.2 переформулировать: «доля клипнутых баров на train
  < порога» (для affine-скейлеров p1..p99 больше не применяется — их нет).
- Утечка скользящего окна: rolling ТОЛЬКО `.shift(1)` (строго прошлое, без
  текущего бара); прогрев окна заполнять вперёд/нулём/нейтралью, НЕ bfill;
  гейт: признак на префиксе [0:t] == на полном ряде в точке t (иначе заглядывание).
