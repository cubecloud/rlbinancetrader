## 1. Что именно меряем

**Oracle-резерв** = верхняя граница пользы от свободы раннего выхода из
dip-сделок, при идеальном знании будущего, но при СТРОГОЙ семантике движка.

Oracle-политике (и только ей, см. `v7hook.py:33-45`) разрешено видеть будущее.
Механика раннего выхода — через `AgentHookBT.exit_policy`: агентский выход
вызывается ПОСЛЕ штатного `next()`, поэтому «позже штатного нельзя»
гарантировано структурой хука (`v7hook.py:4-7, 47-67`). Разрешён только dip;
transition запрещены (`v7hook.py:11, 60`).

**Цена выхода — строго `open(i+1)`** (решение на баре i → исполнение по открытию
следующего бара, с комиссией 0.001). НИКАКОГО `max(High)` внутри сделки.
Это ровно то, что исполняет `position.close()` в хуке при `trade_on_close=False`.

### Oracle-политика (определение, обеспечивающее дельту ≥ 0 по построению)
Для каждой dip-сделки с границами `[entry_bar, exit_bar]` (границы чистой v7):
- **hook-eligible бары исполнения** = `[entry_bar+2 .. exit_bar-1]`
  (на `entry_bar` позиция ещё не открыта внутри `next()`; на баре механического
  решения `exit_bar-1` родитель уже закрыл — хук заблокирован; исполнение
  раннего выхода не может быть позже `exit_bar-1`). Это консервативная граница:
  никогда не завышает то, что реально может хук.
- `price_oracle = max(open[b] * (1 - commission))` по eligible-барам исполнения.
- Ранний выход берётся, ТОЛЬКО если `price_oracle > price_exit_v7`; иначе
  сделка держится до штатного выхода. Отсюда **дельта ≥ 0 всегда** — oracle
  выбирает максимум из {лучший ранний пик, держать до механики}. Это НЕ «всегда
  выйти в будущий пик»; потеря на винерах структурно возможна только через
  knock-on полного движка (см. §4).

Замечание о механике cooldown (находка советника, подтверждена кодом):
агентский `position.close()` НЕ ставит `_await_signal_close`
(`v7hook.py:8-10, 63-65`), поэтому родитель на следующем баре взводит cooldown
на `cooldown_bars=423` бара как после SL (`regimeb_bt_strategy.py:276-277`).
Значит **каждый** ранний выход oracle вводит 423-барный cooldown. Для dip-сделок,
которые в v7 закрывались signal/legflip (там cooldown НЕ взводился), это НОВЫЙ
cooldown → давление на последующие входы, часть которых TP-винеры. Это главный
канал «потери на винерах» и предмет отдельного замера цены cooldown (§5).

## 3. Декомпозиция резерва (не одно число)

Всё в **frozen-пространстве** (посделочные `ReturnPct` на исходных границах v7).
Разложение по причине выхода базы v7 (тождество по построению):

- **(б) экономия на лузерах = сумма frozen-дельт по dip-сделкам с
  `exit_reason == "sl"`** (те, что дошли бы до SL). ЭТО КОМПОНЕНТА ГЕЙТА.
- экономия на прочих лузерах: dip с `signal`/`legflip`, закрытых в минус.
- (потенциальная) потеря/нейтраль на **винерах** `exit_reason == "tp"`:
  на frozen ≥ 0 по построению; реальная потеря на винерах — только в §4/§5.
- диагностика хвостов (§6).

**Partition-identity (обязательный тест):** сумма дельт по всем бакетам
(`sl + tp + signal + legflip`) == полный frozen-резерв, ровно, по построению.
Это тождество ВНУТРИ frozen. Компаунд движка живёт в других единицах
(сайзинг 0.9999 + целые лоты, `v7runner.py:147-150`) — сводить frozen к
компаунду НЕ пытаемся.

## 4. Тройной отчёт сравнения (обязателен, по каждой эпохе)

1. **A. Frozen (парные дельты).** Посделочные дельты на исходных границах v7.
   Никаких cooldown/CB-эффектов. Декомпозиция §3. Это пространство гейта.
2. **B. Полный прогон движком.** `exit_policy` выходит на предрасчитанных
   оптимальных барах решения (`decision_bar = fill_bar - 1`). Пересчитываются
   cooldown/CB/подавленные transition ПОЛНЫМ движком.
   `Reserve_B = Return_oracle − Return_v7` (п.п. движкового Return).
3. **C. Разность («цена knock-on»), ОТДЕЛЬНОЙ строкой.** Складывается из:
   - **цена cooldown** = `Return_oracle(cooldown отключён) − Return_oracle(cooldown как есть)` —
     чистая величина в одних единицах, см. §5;
   - **CB-дивергенция / подавленные transition** — как СЧЁТЧИКИ разницы
     трейдбука (Δn сделок, Δn transition, Δn CB-срабатываний) между прогоном
     oracle и v7. НЕ сводится арифметически к A (сайзинг) — репортится честно
     как остаток, а не тождество.

## 5. Отдельный замер цены cooldown-правила

Подкласс `AgentHookBT` в `spotrl/analysis/` (strategy_rl не трогаем, но
наследование/импорт разрешён), в котором после агентского `position.close()`
ставится `self._await_signal_close = True` → cooldown агентским выходом НЕ
взводится. Тогда:

- `cooldown_price = Reserve_B(disarmed) − Reserve_B(as-is)` (обе величины —
  полный движок, одни единицы, вычитание корректно).
- Диагностика: число НОВЫХ cooldown, введённых oracle = число early-exit на
  dip-сделках, чья база-причина ≠ sl. Печатается по эпохе.

**Порог эскалации (предложение, требует утверждения):** если цена cooldown
съедает **≥ 50%** валового frozen-резерва компоненты (б) в эпохе — правило
cooldown выносится пользователю на пересмотр ОТДЕЛЬНЫМ решением (не частью
вердикта жив/мёртв).

## 6. Метрики хвостов (по каждой эпохе)

- **tail-capture ratio** = frozen-резерв / справочный идеальный потолок по
  `max(High)` внутри окна (СПРАВКА, не цена сделки; показывает, какую долю
  теоретического максимума ловит реалистичный `open(i+1)`-oracle).
- **leave-top-k-out (k=1..3):** frozen-резерв после удаления k dip-сделок с
  наибольшей дельтой. Тест на хрупкость (весь ли резерв держится на 1–2
  везучих сделках).
- **доля сохранённых TP:** из dip-сделок с `exit_reason=="tp"` в v7 — доля тех,
  которые oracle НЕ выводит раньше (ожидается близко к 1.0).

## 7. ПОРОГИ ЧИСЛАМИ (предложения; требуют утверждения ДО вердикта)

| # | Что | Порог (предложение) | Знаменатель / формула |
|---|---|---|---|
| П1 | **Гейт (б): свобода мертва** | компонента (б) **< 0.5%/сделку** → мертва в этой эпохе | `Σ frozen-дельта по dip-SL / n_dip эпохи` (A: /146, B: /245) |
| П2 | Цена cooldown → пересмотр правила | **≥ 50%** валового резерва (б) | см. §5, отдельное решение |
| П3 | Хрупкость резерва | leave-top-3-out убирает **≥ 50%** frozen-резерва → «резерв держится на единицах сделок» | §6 |
| П4 | Сохранность TP | доля сохранённых TP **< 0.9** → тревога «oracle рубит винеры» (репорт, не гейт) | §6 |

**Ключевая неоднозначность знаменателя П1, вынесена на утверждение.**
Формулировка плана «< 0.5%/сделку … отдельно по 146 dip-сделкам»
(`PLAN.md:1400-1401`) допускает два знаменателя:
- (по всем dip эпохи): `Σ дельта / n_dip` — предлагаемая формула (A: /146, B: /245);
- (по SL-обречённым dip): `Σ дельта / n_dip_sl` (A: /9, B: /37) — даёт число
  в ~13–16 раз больше.
Это меняет вердикт. Предлагается знаменатель = **все dip эпохи** (консервативно:
резерв «размазан» по всем сделкам, ведь агент не знает заранее, какая дойдёт до
SL). Обе величины будут напечатаны; вердикт применяется только после
утверждения знаменателя пользователем.

**Anchor-inflated:** по эпохе A компаунд-числа (Reserve_B) помечаются
anchor-inflated и не используются как основной аргумент; гейт П1 — на frozen,
он от компаунда не зависит.

## 8. Тесты харнесса (гейт Э0.4: покрытие ≥85%, быстрый набор ≤60 с)

- **T1 anti-future:** oracle не использует бары за пределами `[entry, exit]`
  своей сделки и не использует `High` (только `open`); перестановка баров
  ПОСЛЕ `exit_bar` не меняет результат.
- **T2 open(i+1)-семантика:** цена раннего выхода на синтетике равна
  `open[decision_bar+1]*(1-commission)`, не `close`, не `open[decision_bar]`.
- **T3 partition-identity:** сумма бакетных дельт == полный frozen-резерв
  (равенство до 1e-9).
- **T4 delta ≥ 0:** ни одна frozen-дельта не отрицательна.
- **T5 cooldown-disarm:** агентская ветка выхода исполняется в режиме
  «cooldown отключён»; цена cooldown ИЗМЕРЯЕТСЯ, но её знак НЕ предполагается.
  (Гипотеза «disarm ≥ as-is» снята: в компаунде с предвидением она неверна,
  см. impl-отчёт, замечание о path-chaotic компаунде.)
- **T6 сверка базы:** чистая v7 совпадает с судьёй по границам (на срезе).
